## 三、A-1:8 条文案在英文机上显示中文(已修)

### 怎么发现的
不是靠肉眼看 `.xcstrings`。做法是打开编译期字符串提取(`SWIFT_EMIT_LOC_STRINGS=YES`),拿到编译器实际抽出的 **340 个源码 key**,再和 **编译产物** `Vela.app/en.lproj/Localizable.strings` + `Localizable.stringsdict` 做集合差。这样能抓到「源码文案改了但字符串目录没跟上」这种静默失败(缺 key 不报错,直接回退成中文)。

### 缺的 8 条(改前)

| 源码位置 | 中文原文(节选) |
|---|---|
| `Sources/Views/SettingsView.swift:371` | 已开启:数据同步到你自己的 iCloud 私有库… |
| `Sources/Views/SettingsView.swift:372` | 开启后,数据存到你自己的 iCloud 私有库… |
| `Sources/Views/SettingsView.swift:352` | 双向同步经期:导入「健康」里最近 180 天… |
| `Sources/Views/SettingsView.swift:427` | 无法连接 Apple 健康 |
| `Sources/Views/SettingsView.swift:430` | 未能获得「健康」App 的经期读写授权… |
| `Sources/Views/CalendarView.swift:116` | 导出失败 |
| `Sources/Views/CalendarView.swift:119` | 未能生成导出文件,请检查设备存储空间后重试。 |
| `Sources/Support/Store.swift:56` | 有一笔交易未能通过签名校验,已跳过。 |

**为什么算 P1**:App Store 主语言是 English (U.S.),截图也是英文。审核员打开「设置」页看 iCloud 同步和 Apple 健康两段说明,看到的是中文段落 —— 这两段恰好是隐私卖点的核心说明。属于 Guideline 2.3(准确的元数据 / 完整度)的常见追问点。

### 修法
`Resources/Localizable.xcstrings` 补 8 条 en + zh-Hans。**纯新增**(diff:+129 / −1,−1 是文件末尾的括号行),没有动任何已有翻译。

### 复验
重新构建后再跑一次同样的集合差:

```
en:      350 条 | 未翻译源码 key:3 → ['%lld', '%lld / %lld', 'Maren']
zh-Hans: 350 条 | 未翻译源码 key:3 → 同上
```

剩下这 3 条是**纯数字格式串和品牌名**(`Text("\(i)")`、`Text("\(value) / \(range.upperBound)")`、`"Maren"`),任何语言下渲染结果都一样,不需要翻译,可忽略。

> 复数形式(`%lld 天`、`本月记录经期 %lld 天` 等)会被编进 `Localizable.stringsdict` 而不是 `.strings`,第一次比对时它们看起来"缺失"是假阳性;本次比对已把 stringsdict 一并计入,结论可信。

### A-3 顺带处理
已提交版本(`9207cf7`)的字符串目录是干净的:342 个 key、`sourceLanguage: zh-Hans`、0 条 `extractionState`。但**只要跑一次构建**(Xcode 或 `xcodebuild` 都会),它就会被回写:

1. 给这一轮没编到的 key 批量加上 `"extractionState": "stale"`(本轮实测 272 条);
2. 插入一批**没有任何翻译的空壳 key**(`%@` 形式,对应 `%lld` 的同名条目);
3. 其中一次还把 `sourceLanguage` 从 `zh-Hans` 改成了 `en`。

第 3 条要盯紧(会改变编译语义)。第 1、2 条是噪音:**`stale` 条目仍然会被编进 `.strings`** —— 实测 `完成` 标着 stale,编译产物 `en.lproj` 里照样有 `"Done"`。所以 stale ≠ 翻译丢失;本轮翻译丢失的真正原因是**目录里根本没有那 8 条 key**(§三),这在已提交版本里同样存在。

**以后注意**:提交前跑一次 `git diff Resources/*.xcstrings`,确认 diff 里只有「新增翻译」;出现 `sourceLanguage` 变更、大批 `extractionState` 或空 `{}` 条目,就 `git checkout` 还原后重新补翻译(本轮用的脚本:`patch_catalog.py`,先 checkout 再插 8 条,输出稳定可重复)。判断翻译全不全,别看目录文件,看编译产物(§三的方法)。

## 四、A-2:App Privacy 问卷 —— 需要你决策

### 矛盾在哪

- `AppStore/privacy-policy.md`(已托管、已填进 ASC)白纸黑字:**"We do not operate any server that stores your health data. We cannot read it."**、**"We do not collect your name, email…"**
- 但 `AppStore/ASC-上架填写清单.md` §3 和 `AppStore/上架操作手册-逐步点击.md` B3 都让你在问卷里选 **"Yes, we collect data" → Health & Fitness**。

这两个说法不能同时成立。**隐私标签与隐私政策不一致,本身就是 Guideline 5.1.1(i) 的拒审理由**。

### 事实依据

Apple 对 "Collect" 的定义是:**把数据传出设备,并且你或你的第三方伙伴能在实时响应之外的时间访问它**。对照 Maren:

- HealthKit 数据:只在本机读写,不出设备 → 不算 collect。
- CloudKit 私有库:确实出设备了,但落在**用户自己的 iCloud**,开发者无任何访问途径 → 不算 collect。
- 购买状态:由 Apple StoreKit 处理,Apple 自己的支付流程无需申报。
- 无分析 SDK、无账号体系、无广告标识符 → 已代码核验。

### 两个选项

| | 选项 A(推荐)**Data Not Collected** | 选项 B **申报 Health & Fitness** |
|---|---|---|
| 事实准确性 | ✅ 符合 Apple 对 collect 的定义 | ❌ 你并没有把健康数据传到自己服务器 |
| 与隐私政策/官网一致 | ✅ 一致 | ❌ 直接打架,审核员对读会追问 |
| 商店页面呈现 | 「Data Not Collected」徽章 —— 正是核心差异化卖点(打 Flo/Clue) | 「Data Collected: Health & Fitness」—— 卖点被自己抹掉 |
| 风险 | 极小:同类"本地 + 私有 iCloud"的隐私优先 app 普遍这么填 | 与政策不一致导致 5.1.1(i) 追问;上线后想改标签要重新提交 |

**推荐 A。** 理由:它是事实,而且和你已经上线的隐私政策、官网、App 内文案完全对齐。

### 具体怎么操作(选 A)

1. appstoreconnect.apple.com → 你的 App → 左栏 **General → App Privacy**。
2. 「Data Collection」区右上角点 **Edit**。
3. 问题「Do you or your third-party partners collect data from this app?」选 **"No, we do not collect data from this app"**。
4. 点 **Save** → 回到 App Privacy 页点 **Publish**(不 Publish 不生效)。
5. 如果之前已经勾了 Health & Fitness:先在数据类型列表里把 Health & Fitness 取消勾选,再按 3–4 步改成 No。

> 你说 ASC 除截图外都填完了 —— 这一项**很可能已经按旧文档填成了 B**,请务必回去核对一遍。

## 五、CloudKit:真机同步 → Deploy to Production 完整操作

> 这是你问的重点。**必须做**:Xcode 直接跑的 Debug 构建用的是 CloudKit 的 **Development** 环境;**TestFlight 和 App Store 构建用的是 Production 环境**。Production 里如果没有 schema,正式用户开同步会静默失败(数据只留本机,不报错)。

### 顺序总览

```
① 真机跑 Debug 版 → 开同步 → 造全量数据(建 Development schema)
② CloudKit Dashboard 确认 Development schema 完整
③ Deploy Schema Changes → Deploy to Production
④ Production 环境复查
⑤ (之后)TestFlight 装包再验一次真实生产同步
```

---

### 步骤 ① 真机跑一次,把 schema 建到 Development

**为什么要真机**:模拟器不带 iCloud/HealthKit entitlement(本轮已验证:模拟器构建的 `.xcent` 是空的),CloudKit 在模拟器上不会真正建 schema。

1. iPhone 用数据线连 Mac(或同一 Wi-Fi 下的无线调试)。
2. 确认 iPhone **已登录 iCloud**:设置 → 顶部你的名字 → iCloud 正常可用。iCloud 空间不足会导致同步挂起。
3. Xcode 打开 `Vela.xcodeproj` → 顶部设备选择器选 **你的 iPhone**(不是模拟器)→ ⌘R 运行。
   - 首次会提示不受信任的开发者:iPhone → 设置 → 通用 → VPN与设备管理 → 点你的开发者证书 → **信任**。
4. App 内:**设置 → 同步 → 打开「iCloud 同步」**。
   - 如果这里显示的是「iCloud 同步当前不可用」而不是开关,说明 `CKContainer.accountStatus()` 不是 `.available` —— 见 §五·排错 1。
5. 会弹「需要重启 Maren」。**从后台上滑彻底杀掉 app,再重新打开。**
   - ⚠️ 这步不能省。`ModelContainer` 只在 `VelaApp.init` 建一次,不重启进程,开关不会生效,schema 也就建不出来。
6. **造数据 —— 5 个模型都要碰到,而且可选字段必须填**:

   | 要建的记录 | 在哪操作 | 对应 CloudKit 记录类型 |
   |---|---|---|
   | 标记 1 天经期 | 日历页点某天 → 标记为经期 | `CD_PeriodDay` |
   | 1 条完整每日记录 | 今天页:心情 + 能量 + 疼痛 + **睡眠小时** + **体重** + 至少 1 个症状 + 备注 → 保存 | `CD_DailyLog` |
   | 1 个自定义追踪项 | 设置 → 自定义追踪项 → ＋ | `CD_CustomSymptom` |
   | 1 个用药 | 设置 → 用药与补剂 → 添加用药 | `CD_Medication` |
   | 给这个药打一次卡 | 今天页 → 今日用药 → 点一下 | `CD_MedicationIntake` |

   ⚠️ **「睡眠小时」和「体重」必须真的填**。它们是模型里仅有的两个可选属性(`sleepHours: Double?` / `weight: Double?`),CloudKit 镜像**只为写过值的字段建列**。从没填过 → Development schema 里就没有 `CD_sleepHours` / `CD_weight` → 部署到生产后,第一个填体重的正式用户会同步失败。

7. 保持 app 在前台、联网,等 **1–2 分钟**让镜像把记录推上去。

---

### 步骤 ② 在 Dashboard 确认 Development schema 完整

1. 浏览器打开 **https://icloud.developer.apple.com/dashboard/**,用你的 **Apple Developer 账号**登录。
2. 进入 **CloudKit Database**。
3. 左上角容器下拉 → 选 **`iCloud.cd.cc.vela`**。
4. 环境切换器(通常在顶部)选 **Development**。
5. 左栏 **Schema → Record Types**,应该看到:
   - `CD_PeriodDay`、`CD_DailyLog`、`CD_CustomSymptom`、`CD_Medication`、`CD_MedicationIntake`
   - 另外会有 Apple 自动建的 `CD_SyncMetadata`、`cloudkit.share` 等系统类型,**正常,别删**。
6. 点开 **`CD_DailyLog`**,逐条确认字段在:
   `CD_dayKey`、`CD_moodRaw`、`CD_energy`、`CD_pain`、**`CD_sleepHours`**、**`CD_weight`**、`CD_symptoms`、`CD_note`、`CD_updatedAt`。
   - 少了 `CD_sleepHours` 或 `CD_weight` → 回步骤 ①-6 把这两个值填上再保存,等 1 分钟刷新页面。
7. (可选,确认数据真的上去了)左栏 **Records** → Database 选 **Private Database** → Zone 选 `com.apple.coredata.cloudkit.zone` → Query,能看到刚才那几条记录。

### 步骤 ③ Deploy to Production

> ⚠️ **不可逆**。生产 schema 只能**新增**字段/类型,不能删除、不能改名、不能改类型。所以务必在数据模型定稿之后再做。Maren 1.0 的 5 个模型本轮已复审确认合规,可以部署。

1. 停在 **Development** 环境的 **Schema** 页。
2. 右上角点 **「Deploy Schema Changes…」**。
3. 弹窗会列出 Development → Production 的差异清单。**逐条看一遍**,应该只有上面那 5 个 `CD_` 记录类型和它们的字段。
4. 点 **Deploy**(可能要再确认一次)。几秒到 1 分钟完成。

---

### 步骤 ④ 复查 Production

1. 环境切换器切到 **Production**。
2. **Schema → Record Types**,确认 5 个 `CD_` 类型和字段都在,尤其 `CD_DailyLog` 里的 `CD_sleepHours` / `CD_weight`。
3. 到这一步,正式版用户开同步就能正常工作了。

### 步骤 ⑤ TestFlight 上验真实生产同步(建议但非必须)

Archive 上传后,用 TestFlight 装到真机 → 开同步 → 重启 app → 记一条 → 回 Dashboard 切 **Production → Records** 查得到,即为通过。

⚠️ **两个正常现象,别当 bug**:
- **Development 和 Production 的数据是完全隔离的两套**。你在 Xcode Debug 版里造的测试数据,换成 TestFlight 版本后**看不到**,这是对的。
- Production 私有库里你只能看到**自己 Apple ID** 的数据。别的用户的数据你永远看不到 —— 这正是隐私卖点成立的技术原因。

### 排错

| 现象 | 原因 / 处理 |
|---|---|
| 设置页显示「iCloud 同步当前不可用」,没有开关 | `CKContainer.accountStatus() != .available`。查:① iPhone 登录了 iCloud 吗 ② Xcode → Vela target → Signing & Capabilities → iCloud 那块有没有红字、容器 `iCloud.cd.cc.vela` 打勾了吗 ③ 报红就点「Try Again」,或 Xcode → Settings → Accounts → Download Manual Profiles |
| 开了同步,Dashboard 里 Schema 一直是空的 | 九成是**没重启 app**(见 ①-5)。其次:设备没网、iCloud 空间满 |
| 「Deploy Schema Changes…」是灰的 | 当前环境不是 Development,或没有待部署的差异(说明已经部署过了) |
| 同步很慢,要重开 app 才见到对面的数据 | 已知取舍:没开 Background Modes → Remote notifications,所以同步只在启动/进前台触发。不影响审核,见下 |
| 两台设备同一天各记一条,出现重复 | 已有 `DedupSweep` 在启动时折叠,属已知并已处理 |

### 一个可选增强(需要你决定)

**要不要开 Push Notifications + Background Modes → Remote notifications?**

| | 选项 A(推荐,1.0 先不动) | 选项 B 现在就加 |
|---|---|---|
| 效果 | 同步在 app 启动/进前台时触发 | CloudKit 推送即时触发,另一台设备的改动几秒内到达 |
| 代价 | 无 | 要改 `project.yml` 加 capability、重跑 `xcodegen generate`、重新签名;多一个 `aps-environment` entitlement;要重新回归测试一遍 |
| 风险 | 多设备用户会觉得"要重开才同步" | 上线前临门一脚改签名配置,徒增变量 |

**推荐 A**:1.0 先按现状上,这个体验差异对单人多设备的串行使用几乎无感;1.0.1 再加,代码改动很小。
