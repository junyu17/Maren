### 🟠 B1（新，高）版本号已"用掉"，本地与 ASC 不同步，靠 Xcode 自动递增兜底

事情比表面复杂 —— **ASC 上的 build 10，本地根本不存在一个标着 10 的产物。**

实测时间线：

| 时间 | 事件 |
|---|---|
| 09:50:37 | `project.yml` 的 `CURRENT_PROJECT_VERSION` 改为 `"10"` |
| 09:54 | **归档** —— 但此时 `xcodegen generate` 还没跑，pbxproj 仍是 9，故归档内部版本为 **`1.1.0 (9)`** |
| 09:56 | Xcode 先以 `cfBundleVersion "9"` 注册 → **`ERROR.ATTRIBUTE.INVALID.DUPLICATE`** |
| 09:56:33 | Xcode 的「Manage Version and Build Number」**自动递增为 `"10"` 重试 → 成功** |
| 10:07:08 | `xcodegen generate` 才跑，pbxproj 这时才变成 10 |

日志实证（同一次分发内先后两个请求体）：

```
httpBody: {"attributes":{"cfBundleShortVersionString":"1.1.0","cfBundleVersion":"9",...}}   → DUPLICATE
httpBody: {"attributes":{"cfBundleShortVersionString":"1.1.0","cfBundleVersion":"10",...}}  → 成功
```

**后果有两层：**

- **当下**：`project.yml` = 10、`pbxproj` = 10，而 **ASC 已占用 10**。若现在原样重新出包，内部版本仍是 10，会再次撞 `DUPLICATE` —— 只不过 Xcode 又会悄悄递增成 11，本地与 ASC 继续错位。**这正是 v5 那次混乱的成因，机制没变，只是被自动递增掩盖了。**
- **长期**：只要开着「Manage Version and Build Number」，归档的内部版本号就永远不等于 ASC 上的版本号，**证据链无法自证**。

**建议（两个方案）：**

- **方案 A（推荐）**：把 `project.yml` 改为 `"11"` → 跑 `xcodegen generate` → **确认 pbxproj 已是 11** → 再归档。并**关闭** Xcode 分发时的「Manage Version and Build Number」，让本地版本号与 ASC 严格一致。
- **方案 B**：继续依赖自动递增，但每次上传后立刻把 ASC 实际版本号回填进 `project.yml` 并重跑 xcodegen。可行但容易漏，不推荐。

> 无论选哪个，**"改完 project.yml 必须先跑 xcodegen 再归档"** 这一步不能省 —— 这次就是漏了它。

### 🔴 A1（阻断）ASC 上的 Build 9 **不含**付费墙 CTA 修复，修复版上传失败了两次

这是本轮最严重的问题：**你花力气修的那个 bug，修复后的二进制根本没进 App Store Connect。**

#### 实测时间线（全部有日志佐证）

| 时间 | 事件 | 证据 |
|---|---|---|
| 05:33:59 | `PaywallView.swift` 修改 | 文件 mtime |
| 05:47:05 | 生成第一个 b9 archive，主二进制 `d8e35e93…` | `Maren-v1.1.0-b9.xcarchive` |
| 06:08:39 | 发起上传 | `Vela_2026-08-24_06-08-39.xcdistributionlogs` |
| **06:10:50** | **`Store.swift` 修改 —— CTA 修复的核心** | 文件 mtime |
| 06:11:07 | **`Upload succeeded`** ← 上传的是 05:47 那个包 | 同上日志 |
| 06:17:49 | 生成 `-final` archive，主二进制 `01b20183…` | `Maren-v1.1.0-b9-final.xcarchive` |
| 06:19 | `** EXPORT SUCCEEDED **` | `build9-final-export.log` |

失败原文：

```
ERROR: [ContentDelivery.Uploader] The provided entity includes an attribute
with a value that has already been used (-19232)
The bundle version must be higher than the previously uploaded version: '9'.
code: ENTITY_ERROR.ATTRIBUTE.INVALID.DUPLICATE
```

#### 结论

**上传成功的那一次（06:08 发起 / 06:11 完成）用的是 05:47 的包，而 CTA 修复在 06:10:50 才写进 `Store.swift`。** 含修复的 `-final` 包两次上传都被 ASC 以「build 号 9 已被占用」拒绝。

两个包确实是不同的二进制，已实测：

```
Maren-v1.1.0-b9.xcarchive       主二进制 sha 前24位: d8e35e93ae20681b90120cae   3,833,120 bytes
Maren-v1.1.0-b9-final.xcarchive 主二进制 sha 前24位: 01b20183650f26fd797fc343   3,849,552 bytes
                                                                          ↑ 差 16,432 bytes
```

两包的 `en.lproj/Localizable.strings` SHA 完全相同，说明差异**纯粹在编译代码**；且 05:47–06:17 之间唯一被改的源文件就是 `Store.swift`。

#### 缺失的正是修复本身

`Store.swift` 06:10:50 那次改动（`git diff` 实证）做了三件事，全部不在 ASC 的包里：

1. 从 `loadProducts()` 里**移除阻塞式 `await checkTrialEligibility()`** —— 这正是真机上 CTA 卡在不可点击 "Choose a plan" 的根因
2. 新增产品批量返回为空时的**逐个 ID 重试**
3. 新增产品加载失败时的**明确错误提示**（原为无反馈死按钮）

**若现在提交，Apple 审核员在真机 + Sandbox 账户下会命中和上一轮一模一样的付费墙死按钮，大概率第三次被拒。**

#### 需要 Billy 做什么

必须出 **Build 10**，不能沿用 9。步骤：

1. 把 `project.yml` 的 `CURRENT_PROJECT_VERSION` 从 `"9"` 改为 `"10"`
2. 跑 `xcodegen generate`
3. 重新 archive → export → upload
4. 在 ASC 确认新构建为 `1.1.0 (10)` 且处理完成后，**再把它选进 Draft Submission**
5. 删除或改名 `Maren-v1.1.0-b9.xcarchive`（见 A3）

> ⚠️ 千万不要试图「重传 build 9」——ASC 的 build 号一旦被占用就永久不可复用，只能递增。

## 三、优化建议（本版新增）

以下**均非拒审问题**，是审计过程中发现的可改进项，按「投入产出比」排序。

### 🥇 O1 性能：核心打卡流程存在全表加载 + 线性扫描

**这是最值得修的一项。**

项目在 `CyclePredictor.swift:69` 已确立「计算有界」原则（`lookbackDays = 730`，注释明确写着"让单次重算的成本有上界,不随使用年限增长"）。但 **`@Query` 数据层没有遵循同一原则** —— 多处无谓词全表查询：

| 位置 | 代码 | 问题 |
|---|---|---|
| `DailyLogView.swift:8` | `@Query private var logs: [DailyLog]` | 加载**全部**每日记录 |
| `DailyLogView.swift:192` | `logs.first { Cal.isSameDay($0.date, day) }` | 为找**一天**的记录，全表物化 + Swift 层线性扫描；且用了派生属性 `date` 而非主键 `dayKey` |
| `DailyLogView.swift:12` | `@Query private var intakes: [MedicationIntake]` | 加载**全部**打卡历史 |
| `DailyLogView.swift:188` | `intakes.filter { $0.dayKey == key }` | 同上，全表扫描取一天 |
| `DailyLogView.swift:573` | `intakes.first(where: { … })` | 同上 |
| `SettingsView.swift:11` | `@Query private var allLogs: [DailyLog]` | 打开设置页即全表加载 |
| `CorrelationExplorerView.swift:16-17` | `medications` / `intakes` 无谓词 | 全表 |
| `CustomSymptomManagerView.swift:10` | `logs` 无谓词 | 全表 |

**为什么值得修**：`DailyLogView` 正是立项书 F3 定义的「**3 秒打卡，极简、不卡**」核心流程。按每天 1 条 DailyLog + 3 条 MedicationIntake 估算，用满 3 年约 **1,100 + 3,300 行**，每次进入打卡页都要全量物化并做 Swift 层线性扫描。新用户完全无感，**重度老用户会逐年变慢** —— 而重度老用户恰恰是订阅续费的核心人群。

**建议方向**（两个方案）：

- **方案 A（推荐，改动小）**：给按天取用的查询加 `#Predicate` 限定 `dayKey`，例如 `@Query(filter: #Predicate<DailyLog> { $0.dayKey == key })`。符合 CLAUDE.md「`#Predicate` 里只能用 `dayKey`」的既定约定，改动集中在 3–5 处。
- **方案 B（彻底，改动大）**：比照 `CyclePredictor` 引入统一的 `lookbackDays` 窗口，所有趋势/相关性类视图只查窗口内数据。收益更大但涉及面广，适合放到 1.2.0。

> ⚠️ 无论选哪个，**都不要在本轮改** —— 已上传的 build 7 一动就作废全部现有证据。这是 1.1.1 / 1.2.0 的事。

### 🥈 O2 ASO：关键词有 20 字符浪费，且含两个与审核回复矛盾的词

当前配置（`AppStore/ASC-上架填写清单.md`）：

```
App Name : "Maren: Period & Mood"          (20/30)
Subtitle : "Private period & mood tracker" (29/30)
Keywords : period tracker,cycle,menstrual,PCOS,ovulation,mood,symptom,
           privacy,irregular,calendar,pms,fertility   (99/100)
```

**问题 1 —— 浪费 20 个字符**：Apple 的搜索索引会把 **App Name + Subtitle** 的词一并纳入，无需在 Keywords 里重复。已被索引的词为 `maren / period / private / mood / tracker`，而 Keywords 里的 `period tracker`（14 字符）和 `mood`（5 字符）+ 分隔符 = **20 字符纯浪费**，占了 100 字符预算的 1/5。

**问题 2 —— 🔴 `ovulation` 与 `fertility` 与你给 Apple 的回复直接矛盾**：

`01-Apple-Review-Reply-EN.md` §3 明确写着 app「does not provide … a **fertility** guarantee, **ovulation** interpretation, safe-period calculation」。而 Keywords 里却买了这两个词。这既违反 CLAUDE.md 铁律 3，也存在 **Guideline 2.3.1（元数据须准确）** 的一致性风险——审核员会同时看到这两处。

**建议**：删掉 `period tracker`、`mood`、`ovulation`、`fertility`，腾出的约 40 字符换成与产品实际定位一致、且竞品覆盖较弱的长尾词。备选方向：`perimenopause`、`cycle log`、`offline`、`no ads`、`local`、`diary`、`health log`。`perimenopause` 尤其值得买 —— 这是 Maren 已实装、而 Flo/Clue 覆盖薄弱的差异化功能。
